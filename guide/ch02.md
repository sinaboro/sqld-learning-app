## 02.1 | 정규화

**정규화**는 데이터의 **중복을 없애고 이상현상을 막기 위해** 테이블을 알맞게 쪼개는 과정이에요. 중복이 있으면 아래 같은 **이상현상(Anomaly)**이 생겨요.

| 이상현상 | 예 (수강 테이블에 학생 주소가 함께 있을 때) |
|---|---|
| 삽입 이상 | 과목을 신청하지 않은 학생은 주소를 저장할 수 없다 |
| 갱신 이상 | 주소가 바뀌면 여러 행을 다 고쳐야 하고, 하나라도 빠지면 불일치 |
| 삭제 이상 | 마지막 수강 기록을 지우면 학생 주소까지 사라진다 |

### 함수적 종속

`A → B` 는 "A 값을 알면 B 값이 하나로 정해진다"는 뜻이에요. 이때 A 를 **결정자**, B 를 **종속자**라고 합니다. (사원번호 → 이름)

### 정규형 단계

| 정규형 | 조건 | 해결 방법 |
|---|---|---|
| 1정규형 (1NF) | 모든 속성이 **원자값**(하나의 값) | 다중값·반복 속성을 행이나 별도 테이블로 분리 |
| 2정규형 (2NF) | 1NF + **부분 함수 종속 제거** (복합 PK 의 일부에만 종속된 속성이 없음) | 일부 키에만 종속된 속성을 분리 |
| 3정규형 (3NF) | 2NF + **이행 함수 종속 제거** (A→B, B→C 일 때 A→C 없앰) | 키가 아닌 속성에 종속된 속성을 분리 |
| BCNF | 3NF + **모든 결정자가 후보키** | 후보키가 아닌 결정자를 분리 |

```text
[수강] (학번, 과목코드) → 성적          ← 완전 함수 종속 OK
       학번 → 학생이름                  ← 부분 함수 종속 → 2NF 위반 → [학생] 분리
[사원] 사원번호 → 부서번호 → 부서명     ← 이행 함수 종속 → 3NF 위반 → [부서] 분리
```

> 💡 우리 예제 DB 도 정규화되어 있어요. 사원(EMP)에는 부서번호만 있고, 부서명은 부서(DEPT)에 따로 있죠. 이행 종속(사원번호 → 부서번호 → 부서명)을 없앤 3정규형입니다.

### 반정규화 (역정규화)

정규화된 모델에서 **조회 성능**을 높이려고 일부러 중복을 허용하거나 테이블을 합치는 것이에요. 단, **데이터 무결성이 깨질 위험**이 있으니 꼭 필요할 때만 합니다.

| 대상 | 기법 |
|---|---|
| 테이블 | 테이블 병합(1:1, 1:M, 슈퍼/서브타입), 테이블 분할(수직·수평), 중복 테이블 추가(통계·이력·부분 테이블) |
| 칼럼 | 중복 칼럼 추가, 파생 칼럼 추가, 이력 테이블에 칼럼 추가, PK 에 의한 칼럼 추가, 응용 오작동 대비 칼럼 추가 |
| 관계 | 중복 관계 추가 |

> 💡 반정규화 절차: ① 반정규화 대상 조사 (범위·빈도·통계) → ② **다른 방법 먼저 검토** (뷰, 클러스터링, 인덱스, 응용 프로그램) → ③ 반정규화 적용.

## 02.2 | 관계와 조인의 이해

모델에서 엔터티 사이의 **관계**는 SQL 에서 **조인(JOIN)**으로 다시 이어 붙여 조회해요. 부서(1)와 사원(M)의 관계는 사원의 FK(DEPTNO)와 부서의 PK(DEPTNO)를 같게 놓고 조인합니다.

```sql
-- 관계(부서 1 : 사원 M)를 조인으로 표현: 사원 이름과 부서 이름 함께 보기
SELECT E.ENAME, E.DEPTNO, D.DNAME
FROM EMP E, DEPT D
WHERE E.DEPTNO = D.DEPTNO        -- FK = PK 로 관계를 잇는다
  AND E.DEPTNO = 10;
```

### 순환 관계 (자기 참조)

한 엔터티가 **자기 자신과 관계**를 맺는 것이에요. 사원의 관리자(MGR)도 사원이죠. 같은 테이블을 두 번 써서 조인합니다(셀프 조인, 2과목에서 자세히).

```sql
-- 사원과 그 관리자 이름
SELECT W.ENAME AS 사원, M.ENAME AS 관리자
FROM EMP W, EMP M
WHERE W.MGR = M.EMPNO AND W.DEPTNO = 20;
```

### 상호배타 관계

하나의 엔터티가 두 엔터티 중 **하나와만** 관계를 맺는 것이에요. 예: 주문은 개인고객 **또는** 법인고객 중 한쪽에만 연결됩니다. (ERD 에서 관계선에 호를 그려 표시)

+ 순환 관계
- 식별 관계
- M:N 관계
= 같은 엔터티끼리의 관계를 순환(재귀, 자기 참조) 관계라고 해요.

+ 상호배타 관계
- 순환 관계
- 존재 관계
- 1:1 관계

- 사원의 PK 와 부서의 PK
+ 사원의 FK(부서번호)와 부서의 PK(부서번호)

= 자식의 FK 와 부서의 PK 를 같게 놓아 관계를 이어요.

## 02.3 | 모델이 표현하는 트랜잭션의 이해

**트랜잭션**은 **함께 성공하거나 함께 실패해야 하는 작업 묶음**이에요. 계좌 이체에서 출금과 입금은 둘 다 되거나 둘 다 안 되어야 하죠.

### 트랜잭션의 4가지 성질 (ACID)

| 성질 | 뜻 |
|---|---|
| 원자성 (Atomicity) | 모두 실행되거나 전혀 실행되지 않는다 (All or Nothing) |
| 일관성 (Consistency) | 실행 전후 데이터베이스가 일관된 상태를 유지한다 |
| 고립성 (Isolation) | 실행 중인 트랜잭션은 다른 트랜잭션의 영향을 받지 않는다 |
| 지속성 (Durability) | 완료(커밋)된 결과는 영구히 저장된다 |

### 모델에서 트랜잭션 읽기

주문과 주문상세처럼 **반드시 함께 생겨야 하는** 엔터티는 관계를 **필수(Mandatory)**로 표현해요. 주문만 있고 주문상세가 없는 상태가 되면 안 되므로, 두 INSERT 를 하나의 트랜잭션으로 묶어 처리합니다.

```sql
-- 부서와 그 부서의 첫 사원을 하나의 트랜잭션으로 등록
BEGIN;
INSERT INTO DEPT VALUES (50, 'MARKETING', 'SEOUL');
INSERT INTO EMP (EMPNO, ENAME, JOB, SAL, DEPTNO) VALUES (8001, 'KIM', 'MANAGER', 3000, 50);
COMMIT;
SELECT D.DNAME, E.ENAME FROM DEPT D, EMP E WHERE D.DEPTNO = E.DEPTNO AND D.DEPTNO = 50;
```

+ 원자성
- 일관성
- 고립성
- 지속성
= All or Nothing 은 원자성(Atomicity)이에요.
? 커밋된 결과가 시스템 장애가 나도 유지되는 성질은?
- 원자성
- 고립성
+ 지속성
- 일관성
= 완료된 결과가 영구히 남는 것이 지속성이에요.
? 주문과 주문상세처럼 반드시 함께 생겨야 하는 관계를 모델에서 표현하는 방법은?
- 선택 관계로 표시한다
+ 필수 관계로 표시한다
- 관계를 없앤다
- 상호배타 관계로 표시한다
= 함께 발생해야 하는 엔터티는 필수 관계로 표현해 하나의 트랜잭션으로 처리해요.
@end

## 02.4 | NULL 속성의 이해

**NULL** 은 "값이 **없음**, 아직 **모름**"을 뜻해요. 0 이나 공백 문자와 **다릅니다.** EMP 의 COMM(커미션)은 영업사원 말고는 NULL 이에요.

### NULL 규칙 4가지

| 규칙 | 예 | 결과 |
|---|---|---|
| NULL 과의 **산술 연산**은 NULL | 1000 + NULL | NULL |
| NULL 과의 **비교**는 알 수 없음(UNKNOWN) → 조건이 거짓처럼 동작 | COMM = NULL | 행이 안 나옴 |
| NULL 확인은 **IS NULL / IS NOT NULL** | COMM IS NULL | 정상 |
| **집계 함수는 NULL 을 빼고** 계산 (COUNT(*) 제외) | AVG(COMM) | NULL 아닌 4건의 평균 |

```sql
-- 산술 연산: COMM 이 NULL 이면 결과도 NULL
SELECT ENAME, SAL, COMM, SAL + COMM AS 합계 FROM EMP WHERE DEPTNO = 30;
```

```sql
-- = NULL 은 아무 행도 못 찾는다, IS NULL 을 써야 한다
SELECT COUNT(*) AS "= NULL" FROM EMP WHERE COMM = NULL;
SELECT COUNT(*) AS "IS NULL" FROM EMP WHERE COMM IS NULL;
```

```sql
-- 집계 함수와 NULL: COUNT(*) 는 모든 행, COUNT(COMM) 은 NULL 이 아닌 행만
SELECT COUNT(*), COUNT(COMM), SUM(COMM), AVG(COMM), AVG(NVL(COMM, 0)) FROM EMP;
```

> 💡 AVG(COMM) 은 NULL 이 아닌 4명(300, 500, 1400, 0)의 평균 550, AVG(NVL(COMM, 0)) 은 14명 전체로 나눈 157.1429 예요. **NULL 을 0 으로 볼지** 에 따라 결과가 달라지니 시험에 자주 나와요.

!> 오라클에서는 빈 문자열 `''` 을 NULL 로 취급하지만, SQL Server·SQLite 등은 빈 문자열과 NULL 을 구분해요. SQLD 는 오라클 기준으로 출제됩니다.

- COMM = NULL

## 02.5 | 본질식별자 vs 인조식별자

- **본질식별자**: 업무에 원래 있는 값으로 만든 식별자 (주문번호 + 상품번호)
- **인조식별자**: 일련번호처럼 **인위적으로 만든** 식별자 (주문상세번호 1, 2, 3 …)

| 구분 | 본질식별자 | 인조식별자 |
|---|---|---|
| 장점 | 업무 의미가 분명, 중복 데이터 방지 | PK 가 단순, 조인·관리가 쉬움 |
| 단점 | 여러 속성으로 PK 가 복잡해질 수 있음 | **중복 데이터 발생 가능**, 불필요한 인덱스 추가 |

```sql
-- 인조식별자만 PK 로 쓰면 같은 내용이 중복으로 들어가도 막지 못한다
CREATE TABLE ORDER_ITEM (ITEM_ID INTEGER PRIMARY KEY, ORDER_NO INTEGER, PROD_NO INTEGER, QTY INTEGER);
INSERT INTO ORDER_ITEM VALUES (1, 100, 7, 2);
INSERT INTO ORDER_ITEM VALUES (2, 100, 7, 2);   -- 같은 주문·같은 상품이 또 들어감
SELECT * FROM ORDER_ITEM;
```

```sql error
-- 본질식별자 (주문번호 + 상품번호) 로 PK 를 잡으면 중복을 막는다
CREATE TABLE ORDER_ITEM2 (ORDER_NO INTEGER, PROD_NO INTEGER, QTY INTEGER, PRIMARY KEY (ORDER_NO, PROD_NO));
INSERT INTO ORDER_ITEM2 VALUES (100, 7, 2);
INSERT INTO ORDER_ITEM2 VALUES (100, 7, 2);
```

> 💡 인조식별자를 쓸 때는 본질식별자 칼럼에 **유니크 인덱스(UNIQUE)** 를 따로 만들어 중복을 막는 것이 좋아요.

@quiz
? 인조식별자의 단점으로 옳은 것은?

- 업무 의미가 너무 강하다
- 조인이 불가능하다
= 일련번호 PK 만으로는 같은 업무 데이터의 중복을 막지 못해요.
? 업무에 원래 존재하는 값으로 구성한 식별자는?
+ 본질식별자
- 인조식별자
- 보조식별자
- 외부식별자
= 업무 의미가 있는 원래 값으로 만든 식별자는 본질식별자예요.
@end

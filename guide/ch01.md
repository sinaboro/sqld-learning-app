## 01.1 | 데이터 모델의 이해

**데이터 모델링**은 현실 세계의 업무를 데이터베이스로 옮기기 위해 **정보를 구조화해 표현하는 과정**이에요. 건물을 짓기 전에 설계도를 그리는 것과 같아요.

### 모델링의 3가지 특징

| 특징 | 뜻 |
|---|---|
| 추상화 | 현실의 복잡한 내용을 일정한 형식에 맞춰 표현 |
| 단순화 | 누구나 이해하기 쉽게 약속된 표기법으로 표현 |
| 명확화 | 애매함을 없애고 한 가지 뜻으로 정확하게 표현 |

### 모델링의 3가지 관점

- **데이터 관점**: 업무가 **어떤 데이터**를 다루는가 (What, Data)
- **프로세스 관점**: 업무가 **무엇을 하는가** (How, Process)
- **데이터와 프로세스의 상관 관점**: 업무 처리가 데이터에 **어떤 영향**을 주는가 (Interaction)

### 모델링의 3단계

| 단계 | 하는 일 | 특징 |
|---|---|---|
| 개념적 모델링 | 핵심 엔터티와 관계를 찾아 ERD 작성 | 추상화 수준이 가장 높음, 업무 중심 |
| 논리적 모델링 | 키·속성·관계를 정확히 정의, **정규화** 수행 | 재사용성이 높음, DBMS 에 독립적 |
| 물리적 모델링 | 실제 DB 에 맞게 테이블·인덱스·저장 구조 설계 | 성능·보안·저장 공간 고려 |

### 데이터 독립성과 3층 스키마

데이터 구조가 바뀌어도 응용 프로그램이 영향을 덜 받도록 **3층 스키마**로 나눠요.

| 스키마 | 관점 | 설명 |
|---|---|---|
| 외부 스키마 | 사용자 | 사용자·프로그램마다 보는 데이터 (뷰) |
| 개념 스키마 | 통합 | 모든 사용자의 데이터를 통합한 전체 구조 |
| 내부 스키마 | 물리 저장 | 실제 저장 방식 (파일, 인덱스) |

- **논리적 독립성**: 개념 스키마가 바뀌어도 외부 스키마는 영향 없음
- **물리적 독립성**: 내부 스키마가 바뀌어도 개념·외부 스키마는 영향 없음

### ERD 와 좋은 데이터 모델

ERD(Entity Relationship Diagram)는 **엔터티·속성·관계**로 데이터 구조를 그린 그림이에요. 그리는 순서는 ① 엔터티 도출 → ② 엔터티 배치 → ③ 관계 설정 → ④ 관계명 기술 → ⑤ 관계 참여도(차수) → ⑥ 관계 필수 여부 표시입니다.

```text
 [부서 DEPT]                    [사원 EMP]
 # 부서번호    ──────────<    # 사원번호
 * 부서명        1 : N         * 이름
 o 위치                        o 부서번호(FK)
```

!> 모델링할 때 피해야 할 것: **중복**(같은 데이터를 여러 곳에 저장), **비유연성**(작은 업무 변화에도 모델이 크게 바뀜), **비일관성**(데이터끼리 서로 맞지 않음).

## 01.2 | 엔터티

**엔터티(Entity)**는 업무에 필요하고 **저장해서 관리해야 하는 대상**이에요. 사원, 부서, 주문처럼 명사로 표현되고, 테이블이 됩니다. 엔터티 안의 개별 데이터(사원 SMITH 한 명)를 **인스턴스**라고 해요.

### 엔터티의 특징

1. 반드시 해당 **업무에서 필요하고 관리하고자 하는** 정보여야 한다.
2. **유일한 식별자**로 구분할 수 있어야 한다.
3. **인스턴스가 2개 이상**이어야 한다. (하나뿐이면 엔터티가 아님)
4. 업무 **프로세스에 이용**되어야 한다.
5. 반드시 **속성**을 가져야 한다.
6. 다른 엔터티와 **최소 1개 이상의 관계**가 있어야 한다. (코드·통계성 엔터티는 예외 가능)

### 엔터티의 분류

| 기준 | 분류 | 예 |
|---|---|---|
| 유무형 | 유형 엔터티 (물리적 형태가 있음) | 사원, 상품, 강사 |
| | 개념 엔터티 (형태 없는 개념) | 조직, 보험상품 |
| | 사건 엔터티 (업무 수행 중 발생) | 주문, 청구, 수강신청 |
| 발생 시점 | 기본 엔터티 (키 엔터티, 독립적으로 생성) | 사원, 부서, 고객, 상품 |
| | 중심 엔터티 (기본에서 발생, 업무의 중심) | 계약, 주문, 매출 |
| | 행위 엔터티 (2개 이상 엔터티에서 발생, 자주 바뀜) | 주문 이력, 접속 이력 |

> 💡 엔터티 이름은 현업에서 쓰는 용어로, **단수 명사**로, 약어 없이, 유일하게 짓습니다.

= 기본(키) 엔터티는 다른 엔터티에 의존하지 않고 생겨요. (사원, 부서, 고객)

## 01.3 | 속성

**속성(Attribute)**은 엔터티가 가진 **더 이상 나눌 수 없는 최소 단위의 정보**예요. 테이블의 칼럼이 됩니다. 한 속성은 한 인스턴스에서 **하나의 값만** 가져야 해요.

### 특성에 따른 분류

| 분류 | 뜻 | 예 |
|---|---|---|
| 기본 속성 | 업무에서 원래 가진 속성 | 이름, 급여, 입사일 |
| 설계 속성 | 업무에 없지만 설계하며 만든 속성 | 사원번호, 상태코드 |
| 파생 속성 | 다른 속성에서 계산해 낸 속성 | 합계, 평균, 나이 |

> 💡 파생 속성은 원래 값이 바뀌면 함께 고쳐야 해서 **데이터 정합성 문제**가 생길 수 있어요. 꼭 필요할 때만 씁니다.

### 구성 방식·값의 개수에 따른 분류

- **PK(기본키) 속성**: 인스턴스를 식별 / **FK(외래키) 속성**: 다른 엔터티와의 관계 / **일반 속성**: 나머지
- **단순 속성**: 더 나눌 수 없음 (나이) / **복합 속성**: 나눌 수 있음 (주소 → 시·구·동)
- **단일값 속성**: 값이 하나 (주민번호) / **다중값 속성**: 값이 여럿 (전화번호 여러 개) → 별도 엔터티로 분리

### 도메인

속성이 가질 수 있는 **값의 범위**를 도메인이라고 해요. (자료형, 길이, 허용 값, 기본값, 제약조건) 예: 급여는 0 이상 정수, 성별은 'M' 또는 'F'.

```sql
-- 테이블의 칼럼(속성) 확인: EMP 엔터티의 속성들
SELECT EMPNO, ENAME, JOB, SAL, COMM FROM EMP WHERE DEPTNO = 10;
```

## 01.4 | 관계

**관계(Relationship)**는 엔터티의 인스턴스끼리 **논리적으로 연결된 것**이에요. "부서는 사원을 **포함한다**", "고객이 상품을 **주문한다**"처럼 표현합니다.

### 관계의 종류

- **존재 관계**: 존재 자체로 연결 (부서와 사원 — 사원은 부서에 소속)
- **행위 관계**: 어떤 행위가 있어야 연결 (고객이 주문을 **한다**)

### 관계 표기법 3요소

| 요소 | 뜻 | 예 |
|---|---|---|
| 관계명 | 관계의 이름 (양쪽 방향) | 포함한다 / 소속된다 |
| 관계 차수 (카디널리티) | 참여하는 수 | 1:1, 1:M, M:N |
| 관계 선택사양 (선택성) | 반드시 참여하는가 | 필수 / 선택 (IE 표기의 ○) |

```text
 부서 ┼────────○< 사원      → 한 부서에 사원이 0명 이상(선택), 사원은 반드시 한 부서(필수)
 (1)               (M)
```

!> M:N 관계는 관계형 DB 에서 바로 구현할 수 없어요. 두 엔터티 사이에 **교차(연관) 엔터티**를 만들어 1:M + M:1 로 풀어냅니다. (학생 M:N 과목 → 학생 1:M 수강신청 M:1 과목)

### 관계 체크사항

두 엔터티 사이에 **연관 규칙**이 있는가, **정보의 조합**이 발생하는가, 업무 기술서에 관계 **연결을 가능하게 하는 동사**가 있는가, **업무 기술서에 관계 연결에 대한 규칙**이 서술되어 있는가를 확인해요.

+ 행위 관계
- 식별 관계

= 업무 행위로 연결되는 관계는 행위 관계예요.
@end

## 01.5 | 식별자

**식별자(Identifier)**는 엔터티의 인스턴스를 **하나씩 구분해 주는 속성**이에요. 대표 식별자가 주식별자(테이블의 기본키, PK)입니다.

### 주식별자의 4가지 특징

| 특징 | 뜻 |
|---|---|
| 유일성 | 모든 인스턴스를 **유일하게** 구분한다 |
| 최소성 | 유일성을 만족하는 **최소한의 속성**으로 구성한다 |
| 불변성 | 한 번 정하면 값이 **바뀌지 않는다** |
| 존재성 | 반드시 값이 **있어야** 한다 (NULL 불가) |

### 식별자의 분류

| 기준 | 분류 |
|---|---|
| 대표성 | 주식별자 / 보조식별자 (유일하지만 대표가 아님, 참조 관계 연결에 안 씀) |
| 생성 여부 | 내부식별자 (엔터티 안에서 생성) / 외부식별자 (다른 엔터티에서 온 FK) |
| 속성 수 | 단일식별자 (속성 1개) / 복합식별자 (속성 2개 이상) |
| 대체 여부 | 본질식별자 (업무에서 원래 쓰는 값) / 인조식별자 (일련번호처럼 인위적으로 만듦) |

### 식별자 관계 vs 비식별자 관계

| 구분 | 식별자 관계 | 비식별자 관계 |
|---|---|---|
| 부모의 주식별자가 | 자식의 **주식별자 일부**가 됨 | 자식의 **일반 속성(FK)**이 됨 |
| 표기 (IE) | 실선 | 점선 |
| 연결 강도 | 강한 관계 | 약한 관계 |
| 장점 | 조인 없이 부모 키로 바로 조회 | 자식 PK 가 단순, 유연함 |
| 단점 | 자식으로 갈수록 PK 속성이 늘어남 | 부모 정보가 필요하면 조인이 늘어남 |

> 💡 **비식별자 관계를 고르는 경우**: 부모 없이 자식이 생길 수 있을 때(약한 관계), 자식의 주식별자를 독립적으로 구성하고 싶을 때, 식별자 관계로 PK 속성이 너무 많아질 때.

@quiz
? 주식별자의 특징이 아닌 것은?
- 유일성
- 최소성
- 불변성
+ 다양성
= 주식별자의 특징은 유일성·최소성·불변성·존재성이에요.
? 부모 엔터티의 주식별자가 자식 엔터티의 일반 속성이 되는 관계는?
- 식별자 관계
+ 비식별자 관계
- 상호배타 관계
- 순환 관계
= 비식별자 관계에서는 부모 키가 자식의 일반 속성(FK)이 되고 점선으로 표시해요.
? 다른 엔터티와의 관계로 받아온 식별자는?
- 내부식별자
+ 외부식별자
- 보조식별자
- 본질식별자
= 다른 엔터티에서 온 식별자(FK)는 외부식별자예요.
? '주식별자는 반드시 값이 있어야 한다'는 특징은?
- 유일성
- 최소성
- 불변성
+ 존재성
= 주식별자는 NULL 이 될 수 없어요(존재성).
